# 素材导入后的第一次拉片

这次使用本机 GooSpace 项目的 `video-watch` skill，对已经导入测试项目的原片执行了一次实际抽帧，并补充核看画面。当前阶段的结果是 **2 个稳定的人物主体、已检查样本中未见真实动物、34 个自动镜头候选**。34 不是最终镜头数，默认参数明显漏掉了快速剪辑。

本轮只交付拉片结果供检查，没有改写应用的导入链路、角色分组或 3D 重建结果。

## 默认切镜为什么不够

原 helper 未传入最短镜头参数，安装的 PySceneDetect 实际默认 `min_scene_len=15`。在 24 fps 下等于 **0.625 秒**，开头多个短镜头会被合并：第一个候选从 0.000 秒直接延续到 3.208 秒，但密集抽帧清楚显示了人物、脚部、腾空、反应等不同镜头。

与项目中已有的 **47 镜人工纠正参考表**做 ±2 帧的一对一比较：本次 33 个候选切点命中其中 28 个，参考的 46 个切点中漏掉 18 个，另有 5 个候选切点未匹配。即参考切点召回约 **60.9%**、精确率约 **84.8%**。[比较数据](cut-comparison.json)。这份旧表只作为对照，不冒充本轮 skill 的输出。

诊断性补跑同一检测器，将最短镜头改为 1 帧后得到 **93 个候选段**，说明单纯缩短阈值又会把快速运动等画面变化切得过碎。[诊断候选](fast-cuts.json)。这次没有将 93 个候选写入项目，也没有把它们作为通过验收的镜头表。

## 这一阶段的结论

skill 运行成功，抽帧及视觉报告已生成。**默认镜头结果还不能作为后续重建的可靠输入。** 先检查短镜头边界和 A/B 跨镜头身份，确认局部肢体与水印的处理，才能继续用镜头记录驱动分组、代理和动作重建。

当前应用上传流程仍是 `proxy → pts → cuts → detect → people → motion`，尚未接入这套 skill 的视觉分析结果。对应调用在 `studio/router.mjs` 与 `studio/jobs.mjs`。本报告没有把一次离线执行说成已实现导入后自动拉片。
