# MotionStage 混剪视频还原：开发计划、框架建议与验收标准

> 版本：1.0，2026-09-25。状态：实施建议，文中的目标与门槛尚未实测通过。
>
> 适用范围：用户上传自己有权使用的混剪视频，把不同镜头中的素材人物归并为少数成片角色，以相机和角色动作为主要还原对象；可见场景还原可选。
>
> 现有基线：仓库目前只有 JWM 样片原型，正式工作台停留在场景阶段；五阶段角色页是演练，不能当作本计划的已实现部分。现有样片数据、报告和 `data/` 应保留。

## 1. 完成定义与首版边界

**产品完成定义：** 对一段新导入的视频，系统能生成逐镜人物候选；用户能修正并确认“素材人物出场 → 成片角色”的多对一映射；相机与动作处理读取该映射，并输出角色身份稳定、时间与镜头对应的可审查三维结果。每个阶段必须保留来源、版本和未解决问题，不能用演练通过代替正式验收。

首版应支持用户自带而非预置的素材；“任意视频”不等于承诺所有编码和所有画面都能自动求解。建议先声明并验收以下输入范围，再扩展：MP4/MOV，常见 H.264/H.265 视频，最长 2 分钟、最高 1080p、最多 4 人同时可见，音频可选；可变帧率（VFR）必须按实际时间戳处理。超出范围时给出明确原因或预处理选项。具体容量上限、模型效果和处理时长需在 M0 基准试验后固定。

自动化承诺分成三层：

| 层次 | 首版目标 | 人工入口 |
| --- | --- | --- |
| 画面观测 | 自动切镜、找人、镜内跟踪、估计二维关节 | 改切点、补人、删误检、分裂/连接轨迹 |
| 叙事身份 | 系统可提示跨镜相似人物，但不自行决定目标角色 | 用户将任意多条素材轨迹分配到同一成片角色 |
| 三维还原 | 根据观测与人工确认生成相机、固定骨长角色动作和预览 | 调整尺度、关键姿态、接触、相机及不可信镜头 |

单目视频不能唯一确定深度、背面、绝对尺寸或被遮挡动作。系统应把“画面观测”“算法估计”“用户确认”分别标记；低证据镜头允许待审，不得显示为已完成。

## 2. 用户流程与阶段门槛

1. **导入与项目设置**：上传视频，选择 `proxy`（只建立不可见的尺度/地面/接触代理）或 `reconstruct`（另做可见场景）。系统校验媒体并创建独立项目。
2. **素材分析**：生成预览与时间映射、切镜、人物框、镜内轨迹、代表截图和二维姿态；用户修正漏检、误检、切点。
3. **角色确认，子步骤 A：人物归并**：每个素材轨迹分配给某个成片角色或标记忽略。允许同一演员扮演不同目标角色，也允许不同演员扮演同一目标角色。未处理候选阻止正式确认。
4. **角色确认，子步骤 B：角色资产**：确认角色名称、颜色、代表图、比例、骨架和 CL0/CL1/CL2 外观。归并后的身份对后续逐镜实例稳定。
5. **相机与关键动作**：逐镜估计相机与角色二维/三维关键姿态；显示原片叠加和误差，优先解决高风险镜头。场景选项不阻塞此阶段。
6. **连续镜头**：生成固定骨长、接触约束和时间连续的动作及相机曲线；逐镜检查抖动、脚滑、穿插、运动方向与切镜节奏。
7. **交付**：导出视频、角色、动画、相机、镜头时间表和映射清单；在目标软件回读验证。可见场景只在用户选择 `reconstruct` 时属于交付要求。

建议的正式状态为 `draft → analyzed → cast_confirmed → keyframes_confirmed → motion_confirmed → delivered`。场景分支单独记录 `not_requested / pending / approved`；`not_requested` 不等于 `approved`。演练 `demo_passed` 与任何正式状态完全隔离。

## 3. 框架与部署建议

| 层 | 建议 | 选择原因与落地边界 |
| --- | --- | --- |
| Web 界面 | 保留 React、TypeScript、Three.js 和 Vite | 复用现有工作台、WebGL 预览、角色骨架与视频对照；新增正式“项目/素材/角色归并”页面，不把演练页改名冒充正式流程 |
| API | 保留 Node.js 服务，拆成路由、媒体、项目、角色、任务和导出模块 | 继续使用现有版本冲突语义；视频上传改为流式处理，不能沿用当前 2 MB JSON 请求体 |
| 元数据 | 多项目时迁至 SQLite，启用事务与索引；媒体留在项目目录 | 当前单个 `data/project.json` 不适合多个导入项目和可恢复任务；先写迁移/备份脚本，再读旧 JWM 状态 |
| 异步计算 | 独立 Python 分析 worker，Node 只创建任务、查询进度和保存结果 | 人物检测、姿态、相机优化与渲染耗时较长；任务支持取消、重试、失败记录和模型版本固定 |
| 媒体 | FFmpeg/ffprobe 探测、生成预览与精确时间映射，原片只读保存 | 不以 `frameIndex / 24` 处理用户视频；所有采样和回放以源时间戳为准 |
| 模型 | 通过 `Detector`、`Tracker`、`PoseEstimator`、`CameraSolver` 接口接入，先跑对比基准再选定权重 | 业务数据契约与具体模型解耦；记录权重哈希、版本、阈值、设备和推理时长 |
| 部署 | 本机 GPU 完成首版分析；公开网站只负责上传/管理时，计算 worker 需另配适合的 GPU 与队列 | 当前登记的 2 GB VPS 不应被默认视为已具备视频推理容量；部署拓扑需按实测资源确定 |

切镜可评估 PySceneDetect 的 Content/Adaptive 检测，并保留人工改切点；其新版文档已明确处理 VFR 时间戳变化。[PySceneDetect API](https://www.scenedetect.com/docs/head/api.html)、[VFR 迁移说明](https://www.scenedetect.com/docs/latest/api/migration_guide.html)。姿态候选可评估 MMPose 的二维/三维推理接口，但应单独核对所选权重及训练数据许可。[MMPose 推理文档](https://mmpose.readthedocs.io/en/latest/user_guides/inference.html)、[项目许可证](https://github.com/open-mmlab/mmpose/blob/main/LICENSE)。相机有明确三维地标时可使用 PnP 及重投影误差；没有足够地标时只能保留估计与人工审查。[OpenCV PnP 文档](https://docs.opencv.org/4.12.0/d5/d1f/calib3d_solvePnP.html)。

模型许可证是选型门槛之一。例如 Ultralytics 对其 YOLO 代码和模型说明了 AGPL/Enterprise 两种使用路径；在决定产品部署方式前不应直接把它写成默认生产依赖。[Ultralytics 官方许可说明](https://www.ultralytics.com/license)。模型评估应同时记录许可、来源、大小、精度、推理速度和显存。

## 4. 模块边界与数据契约

建议模块：

- `api/projects`：新建项目、选场景模式、读取阶段状态；旧 JWM 兼容读取。
- `api/media`：流式上传、文件哈希、探测、预览、带 Range 的授权读取。
- `api/jobs`：任务领取、心跳、取消、失败、重试、产物版本。
- `analysis/cuts`、`analysis/person`、`analysis/pose`、`analysis/camera`、`analysis/motion`：各自只生成可追溯观测或候选。
- `domain/casting`：素材轨迹与成片角色的绑定、冲突检查、人工修正及正式确认。
- `domain/reconstruction`：按确认映射创建逐镜 `ActorInstance`，求解关键动作与连续动作。
- `exports`：视频、GLB/其他已验证格式、相机与镜头清单；未验证格式不标记完成。

核心关系如下：

| 实体 | 最少字段 | 不变量 |
| --- | --- | --- |
| `Project` | `id, schemaVersion, revision, sceneMode, phase, createdAt` | 每次正式变更产生新版本；项目目录隔离 |
| `MediaSource` | `id, sha256, originalRef, proxyRef, durationUs, width, height, rotation, timebase, ptsMapRef` | 原片不可被分析结果覆盖；时间戳可回溯 |
| `Shot` | `id, startUs, endUs, source, revision` | 同一剪辑内顺序明确，边界不重叠、不漏时间 |
| `SourceTrack` | `id, shotId, startUs, endUs, observationsRef, cropRefs, confidence, provenance` | 只表示镜内一次连续出场，跨切镜不能自动复用 ID |
| `CharacterAsset` | `id, revision, name, color, scale, rigRef, referenceRefs` | 是最终输出的稳定角色，不等于演员身份 |
| `CastingBinding` | `sourceTrackId, characterId|null, disposition, revision, confirmedBy` | 每条有效轨迹恰好绑定一个目标角色或明确忽略 |
| `ActorInstance` | `id, shotId, sourceTrackId, characterId, motionRef` | 每次出场保持独立动作及根轨迹 |
| `CameraTrack` | `shotId, intrinsics, extrinsicsRef, confidence, evidenceRefs` | 独立于可见场景；可静态或随时间变化 |
| `AnalysisJob` | `id, projectId, inputRevision, algorithmVersion, state, progress, error, outputRef` | 失败不能沿用旧分析冒充新结果 |

观测大数组、截图和模型产物存项目文件夹，数据库保存引用及校验。建议目录为 `data/projects/<projectId>/{media,proxies,observations,previews,exports}`；路径只由服务器生成，API 不接受任意文件系统路径。项目状态和任务状态使用事务；写文件采用临时文件、校验后原子替换。SQLite WAL 可让读取与单写入并发，但仍需限制同项目并发编辑。[SQLite WAL 文档](https://sqlite.org/wal.html)。

接口草案：`POST /api/projects`、`POST /api/projects/:id/media`、`POST /api/projects/:id/analysis`、`GET /api/jobs/:id`、`GET /api/projects/:id/cast`、`PATCH /api/projects/:id/cast`、`POST /api/projects/:id/approve-cast`、`GET /api/projects/:id/shots/:shotId/preview`。修改操作携带 `baseRevision`；冲突返回 409，未处理候选返回 422。正式确认同时冻结媒体、切镜、检测和映射版本。重新分析产生候选新版，并提示人工决策需要核对，不能覆盖已确认映射。

## 5. 技术流水线

| 步骤 | 输入 → 输出 | 必须处理的边界 |
| --- | --- | --- |
| 媒体规范化 | 原片 → 元数据、可播放代理、PTS 映射 | VFR、旋转元数据、音频偏移、坏帧、容器差异 |
| 切镜 | 代理/原片 → `Shot` 候选 | 快切、闪白、快速运镜、淡入淡出、空镜；人工改切点 |
| 人物发现 | 每镜采样帧 → 人物框/裁剪 | 背影、遮挡、小人物、多人贴近；低置信度进入待审队列 |
| 镜内跟踪 | 人物框与时间戳 → `SourceTrack` | 遮挡后重现、交叉换位、剪辑边界；跨镜不自动承接轨迹 |
| 用户归并 | 轨迹 → `CastingBinding` | 多对一、同演员分饰、忽略路人、同镜重复角色冲突 |
| 姿态观测 | 轨迹画面 → 2D 关节与遮挡置信度 | 不可见关节不伪装成真实观测 |
| 3D 动作 | 2D 关节、角色骨架、相机候选 → 关键姿态与连续曲线 | 固定骨长、根位移、深度歧义、接触、抖动及动作特色 |
| 相机求解 | 背景特征、人物构图、用户地标 → 相机轨迹 | 运动背景、镜头变焦、缺少可跟踪背景；记录不确定性 |
| 渲染导出 | 已确认角色/动作/相机 → 预览、视频、三维包 | 切点、时长、音频、色彩、坐标系、帧率及目标软件回读 |

场景为 `proxy` 时，不构造可见景物，但仍保留地面、角色接触和尺度假设。相机和角色根运动存在单目尺度耦合，若证据不足，界面要求用户选择尺度依据并标注“估计”。有可见场景时，额外建立场景资产与背景对齐检查；不把场景制作作为动作求解的前置门槛。

M1—M3 是“用户导入并指定最终角色”的首个完整产品闭环；M4—M6 才是“把整段视频还原为可交付三维影片”的闭环。M4S 只对选择可见场景的项目开放，必须完成自己的审查才能交付该模式。两个闭环应分别发布和验收，不能把 M3 的人物映射演示称为视频还原完成。排期需在 M0 取得样例和速度基线后估算；相机/动作与可见场景制作的研究风险明显高于上传和归并界面，建议单独留试验与返工余量。

## 7. 验收数据与方法

测试集至少包含：现有 JWM 样片、不同演员跨镜扮演同一目标角色的混剪、同一演员分饰两个目标角色、多人同框换位、背影与遮挡、空镜、快切、重复片段、变帧率视频和没有足够背景特征的运镜。标注每个镜头的真实切点、可见人物区间、目标叙事角色及可评估的二维关键点；选择其中一段附相机/姿态人工参考。测试素材必须可合法保留在项目中；无法公开的素材仅保存标注协议和脱敏统计。

M0 先冻结评测协议：切点真值是新镜头首个**呈现帧**，以解码后的源呈现帧序号及 PTS 对照，不以固定 fps 推算。预测与真值按最小序号差一对一匹配，允许相差最多 2 个源呈现帧；多报的切点计误检。人物真值的主评测范围为持续至少 0.3 秒、在规范化 720p 画面中可见框高至少 80 px 且头/躯干有足够画面可标注的出场；其他短暂、远景或严重遮挡出场另列分层报告。一个候选轨迹匹配一条真值，要求覆盖该真值至少 50% 的可见时间，且重叠标注帧的框 IoU 中位数至少 0.3；同一候选不能匹配两人。同框交叉后的 ID 串换单列错误，即使轨迹可手动修正也不能算自动跟踪通过。

下表是**拟议放行门槛**，须在 M0 用真实样本确认合理性。统计必须公布分母、样本集、失败镜头和模型版本，不能只报平均值。

| 关口 | 拟议验收标准 | 证据 |
| --- | --- | --- |
| A1 导入 | 范围内测试视频 100% 成功导入、可 seek、音画长度对应；源文件 SHA-256 不变；坏文件失败可解释 | 探测报告、浏览器回放、哈希及失败日志 |
| A2 切镜 | 按上述源呈现帧规则，硬切点召回 ≥95%，并报告精确率；漏检/误检可修正且调整后时间线无缝 | 真值/预测一对一匹配表、PTS 映射、编辑记录 |
| A3 人物候选 | 按上述持续时间、框高及轨迹匹配规则，主评测范围内出场召回 ≥95%；短镜头和低置信度出场单列待审；同框换位 ID 串换逐例报告并可修正 | 逐镜真值对照、轨迹匹配表、漏检与 ID 串换表、截图回看 |
| A4 角色映射 | 所有有效轨迹均绑定或明确忽略；不同演员→同角色、同演员→不同角色均通过；同镜同角色冲突有提示；刷新/重启及版本冲突正确 | 映射清单、API/浏览器测试、历史快照 |
| A5 相机 | 有足够地标的镜头：720p 画面中高置信度地标的中位重投影误差 ≤8 px；证据不足者必须标为待人工确认 | 每镜相机报告、原片叠加与不确定性列表 |
| A6 动作 | 已确认骨架各肢段长度偏差 ≤0.1%；可见 2D 关节在 720p 下中位重投影误差 ≤10 px；落地、击打等关键接触逐镜人工确认 | 骨长/重投影/接触报告、关键画面与连续播放 |
| A7 时间与连续性 | 逐镜起止对应源时间戳；无未解释的角色 ID 跳变、脚滑或明显穿插；导出视频时长与源片相差 ≤1 输出帧，音画同步经抽样确认 | 镜头表、逐帧对照、完整回放记录 |
| A8 交付 | 所有选中目标角色、动作、相机和时间表有可追溯清单；目标格式重新导入后角色数、骨架层级、关键动作和相机采样一致 | 导出清单、回读脚本和目标软件记录 |
| A9 场景选项 | `proxy` 项目不受 G1 阻挡，场景状态为 `not_requested`；`reconstruct` 项目需完成 M4S：场景资产、逐镜背景对齐记录、正式审查和导出回读 | 两模式端到端测试、背景对齐截图与场景回读记录 |

A5/A6 的自动数值只覆盖能标注的画面证据，不能证明真实三维深度。质量报告还要列出空镜、遮挡、模糊、运动背景、镜头快速变化和低置信度区域，供用户重点审查。正式 G2/G3/G4/G5 均须绑定输入与算法版本；上游视频、切点、归并、骨架或尺度改变时，相关下游批准自动失效。

## 8. 稳定性、安全与操作验收

- 上传使用流式写入、类型/容器双重验证、可配置大小和时长限制；未认证用户不得上传、查看原片或修改项目。对外部署前必须加入身份认证和访问控制。
- 任务异常、进程重启、磁盘不足和模型缺失均应留下失败状态；重试不得生成重复项目或覆盖人工编辑。每个任务有明确的输入哈希和结果目录。
- 原片、人工映射和正式确认状态必须可备份及恢复。删除项目、过期清理和媒体保留策略单独设计，默认不自动删除用户视频。
- 代表性浏览器验证覆盖桌面和小屏：多选归并、键盘回看、长列表虚拟化、保存状态、错误与低置信度提示。
- 每次发布执行构建、受影响测试、浏览器导入与归并流程、单个短视频端到端回归及旧 JWM 演练回归；部署后检查任务队列、媒体读取与持久化卷。

## 9. 先决决策与明确未完成项

1. **分析位置**：本机 GPU、用户自有服务器 GPU，或有明确授权的云服务。上传素材是否允许离开本机需由产品设置与用户知情决定。
2. **识别模型**：用 M0 样本比较可用权重、检测召回、镜内 ID 切换、运行时间、显存和许可证；固定模型之前不承诺“一键识别全部人物”。
3. **输入边界**：M0 后确认容量、格式、时长、并发和成本上限，以及超界视频的提示方式。
4. **目标软件**：先确定必须回读的 DCC 版本和格式；现有 Blender 合成样例不能代替真实全片角色、相机与动作回读。
5. **质量表达**：三维输出是基于单目观测的可审查近似还原；需要用户确认尺度和高风险镜头，不宣传为原片真实动捕数据。

这些决策不阻碍先开发 M1 的多项目/媒体基础和 M3 的版本化角色映射，但 M2 的模型接入与性能门槛必须在选型后验收。
